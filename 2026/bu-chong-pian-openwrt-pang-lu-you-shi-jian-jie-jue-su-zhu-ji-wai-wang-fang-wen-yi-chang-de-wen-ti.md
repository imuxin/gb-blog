# 【补充篇】OpenWrt 旁路由实践：解决宿主机外网访问异常的问题

在上一篇文章中，我介绍了如何在 Ubuntu 宿主机上通过虚拟机运行 OpenWrt，并把它配置成旁路由，让宿主机和局域网设备的流量经过 OpenWrt 处理。

整体方案运行之后，内网访问、科学上网、DNS 分流等功能都可以正常工作。但在实际使用过程中，我遇到了一个新的问题：

**从外网访问 Ubuntu 宿主机上的服务时，请求可以进来，但响应流量无法正确返回。**

这篇文章就是对这个问题的补充说明，重点讲清楚问题原因，以及如何通过第二张物理网卡和源地址策略路由来解决。

### 一、当前网络结构

我的宿主机是一台 Ubuntu 服务器，有两张物理网卡：

* `enp6s0`：接入网桥 `br0`，与虚拟机共用
* `enp7s0`：另一张独立物理网卡，准备用来处理外网访问回包

当前主要网络结构如下：

```
主路由器：192.168.1.1
OpenWrt 旁路由虚拟机：192.168.1.2
Ubuntu 宿主机 br0：192.168.1.10
Ubuntu 宿主机 enp7s0：192.168.1.99
```

其中，Ubuntu 宿主机的 `enp6s0` 被加入到了网桥 `br0` 中，虚拟机 OpenWrt 也连接在这个网桥上。

`br0` 的地址是：

```
192.168.1.10/24
```

OpenWrt 虚拟机的地址是：

```
192.168.1.2/24
```

为了让 Ubuntu 宿主机的默认流量经过 OpenWrt，我把宿主机的默认路由改成了：

```
default via 192.168.1.2
```

也就是说，Ubuntu 宿主机自己访问外网时，流量路径是：

```
Ubuntu 宿主机 → OpenWrt 旁路由 → 主路由器 → 外网
```

这个配置对于普通出站访问没有问题。

但是，当我需要从外网访问 Ubuntu 宿主机上的服务时，就出现了异常。

***

### 二、问题现象

假设我在主路由器 `192.168.1.1` 上做了端口转发，把某个外网端口转发到 Ubuntu 宿主机。

外网请求到达 Ubuntu 是没有问题的。

问题出现在回包阶段。

由于 Ubuntu 宿主机的默认路由已经被设置成了：

```
default via 192.168.1.2
```

所以 Ubuntu 收到外部请求之后，响应流量会按照默认路由发给 OpenWrt 旁路由。

路径大概是：

```
外网 → 主路由器 192.168.1.1 → Ubuntu 宿主机
Ubuntu 宿主机 → OpenWrt 旁路由 192.168.1.2 → ?
```

这时问题就来了。

OpenWrt 旁路由并不是这个连接的入口设备，也没有维护这条外网连接的 NAT 状态。对于 OpenWrt 来说，这个回包是一个“来路不明”的连接，很容易被防火墙、NAT 状态或路由规则丢弃。

最终表现就是：

* 外网请求能到 Ubuntu
* Ubuntu 服务本身也在监听
* 但客户端迟迟收不到响应
* 看起来就像“外网访问不了”

本质上，这不是服务本身的问题，而是 **入站路径和出站路径不一致** 导致的。

***

### 三、问题根因：默认路由被旁路由接管

这个问题的核心原因是：

> Ubuntu 宿主机只有一个全局默认路由，而这个默认路由指向了 OpenWrt 旁路由。

当宿主机主动访问外网时，走 OpenWrt 是符合预期的。

但是，当外网访问宿主机时，回包也会走这个默认路由，就不符合预期了。

对于外网访问来说，我们真正希望的路径应该是：

```
外网 → 主路由器 192.168.1.1 → Ubuntu 宿主机
Ubuntu 宿主机 → 主路由器 192.168.1.1 → 外网
```

也就是说：

* 宿主机日常访问外网：继续走 OpenWrt 旁路由 `192.168.1.2`
* 外网访问宿主机服务：回包直接走主路由 `192.168.1.1`

这就需要引入 Linux 的 **策略路由**。

***

### 四、解决思路：用第二张网卡处理外网访问

我的方案是启用第二张物理网卡 `enp7s0`，给它配置一个独立地址：

```
192.168.1.99/32
```

然后让主路由器上的端口转发指向这个地址：

```
192.168.1.99
```

接下来，在 Ubuntu 上配置策略路由：

> 只要流量的源地址是 `192.168.1.99`，就使用独立路由表，从 `enp7s0` 直接走 `192.168.1.1`。

这样，访问路径就变成了：

```
外网 → 主路由器 192.168.1.1 → 192.168.1.99 / enp7s0 / Ubuntu
Ubuntu 回包 src 192.168.1.99 → 主路由器 192.168.1.1 → 外网
```

而宿主机原本的默认出站路径仍然保持不变：

```
Ubuntu br0 / 192.168.1.10 → OpenWrt 旁路由 192.168.1.2 → 外网
```

这样两类流量就被拆开了：

* `192.168.1.10`：宿主机日常流量，走 OpenWrt
* `192.168.1.99`：外网访问服务的回包，走主路由

***

### 五、Netplan 配置

下面是完整的 Netplan 配置示例。

```yaml
network:
  version: 2
  renderer: networkd

  ethernets:
    enp6s0:
      dhcp4: false
      dhcp6: false
      optional: true

    enp7s0:
      dhcp4: false
      dhcp6: false
      optional: true
      addresses:
        - 192.168.1.99/32
      routes:
        - to: 192.168.1.0/24
          scope: link
          table: 99
        - to: default
          via: 192.168.1.1
          table: 99
      routing-policy:
        - from: 192.168.1.99/32
          table: 99
          priority: 99

  bridges:
    br0:
      interfaces:
        - enp6s0
      dhcp4: false
      dhcp6: false
      addresses:
        - 192.168.1.10/24
      routes:
        - to: default
          via: 192.168.1.2
      nameservers:
        addresses:
          - 192.168.1.1
          - 223.5.5.5
      parameters:
        stp: false
        forward-delay: 0
```

这里有几个关键点。

#### 1. br0 继续使用 OpenWrt 作为默认网关

```yaml
routes:
  - to: default
    via: 192.168.1.2
```

这表示宿主机默认出站流量仍然走 OpenWrt 旁路由。

也就是说，我并没有破坏上一篇文章中已经搭建好的旁路由流量路径。

#### 2. enp7s0 使用 192.168.1.99/32

```yaml
addresses:
  - 192.168.1.99/32
```

这里我没有给 `enp7s0` 配置 `192.168.1.99/24`，而是使用了 `/32`。

原因是 Ubuntu 上已经有一个 `br0` 在 `192.168.1.0/24` 网段中。如果第二张网卡也直接配置成 `/24`，系统会出现两个接口同时直连同一个网段的情况，容易带来路由选择和 ARP 混乱。

使用 `/32` 可以更明确地表示：

> `192.168.1.99` 是这个接口自己的地址，但不要自动把整个 `192.168.1.0/24` 都挂到这个接口上。

然后我们再手动给策略路由表添加必要的链路路由。

#### 3. table 99 是专门给 192.168.1.99 使用的路由表

```yaml
routes:
  - to: 192.168.1.0/24
    scope: link
    table: 99
  - to: default
    via: 192.168.1.1
    table: 99
```

这两条路由只存在于 `table 99` 中，不影响系统主路由表。

第一条表示：

```
192.168.1.0/24 在 enp7s0 所在链路上可达
```

第二条表示：

```
默认流量从 192.168.1.1 出去
```

注意，这里的默认路由是在 `table 99` 中，不是主路由表中的默认路由。

#### 4. routing-policy 决定什么时候使用 table 99

```yaml
routing-policy:
  - from: 192.168.1.99/32
    table: 99
    priority: 99
```

这条规则的意思是：

> 当数据包的源地址是 `192.168.1.99` 时，使用 `table 99` 路由表。

这就是整个方案的关键。

当外网访问 `192.168.1.99` 上的服务时，Ubuntu 的响应包源地址自然也是 `192.168.1.99`。于是这个响应包会命中策略路由规则，从 `table 99` 走主路由器 `192.168.1.1` 返回。

而宿主机普通流量使用的是 `192.168.1.10`，不会命中这条规则，因此仍然走默认路由 `192.168.1.2`。

***

### 六、应用配置

修改 Netplan 配置后，建议先使用：

```bash
sudo netplan try
```

确认网络没有断开后，再正式应用：

```bash
sudo netplan apply
```

如果是远程操作服务器，强烈建议使用 `netplan try`，避免配置错误导致 SSH 断连。

***

### 七、验证路由是否符合预期

配置完成后，可以使用下面几条命令检查。

查看策略路由规则：

```bash
ip rule
```

应该能看到类似规则：

```
99: from 192.168.1.99 lookup 99
```

查看 `table 99`：

```bash
ip route show table 99
```

应该能看到类似结果：

```
192.168.1.0/24 dev enp7s0 scope link
default via 192.168.1.1 dev enp7s0
```

然后分别测试不同源地址的路由选择。

测试 `192.168.1.99` 的出站路径：

```bash
ip route get 8.8.8.8 from 192.168.1.99
```

预期结果应该类似：

```
8.8.8.8 via 192.168.1.1 dev enp7s0 src 192.168.1.99
```

测试 `192.168.1.10` 的出站路径：

```bash
ip route get 8.8.8.8 from 192.168.1.10
```

预期结果应该类似：

```
8.8.8.8 via 192.168.1.2 dev br0 src 192.168.1.10
```

如果结果符合上面两条，就说明流量已经被正确拆分：

* `192.168.1.99` 走主路由器
* `192.168.1.10` 走 OpenWrt 旁路由

### 八、处理双网卡同网段的 ARP 问题

因为 `br0` 和 `enp7s0` 都在同一个二层网络里，而且都属于 `192.168.1.0/24` 这个局域网环境，所以还需要额外处理 ARP 问题。

否则可能出现这种情况：

* 主路由器询问 `192.168.1.99` 的 MAC 地址
* Ubuntu 可能用错误的接口响应
* 或者某个接口替另一个接口回答 ARP
* 最终导致流量从错误接口进入或返回

为了避免这种“ARP 串口”，建议添加如下 sysctl 配置。

创建文件：

```bash
sudo nano /etc/sysctl.d/99-multi-nic-arp.conf
```

写入：

```conf
net.ipv4.conf.all.arp_ignore = 1
net.ipv4.conf.all.arp_announce = 2

net.ipv4.conf.br0.arp_ignore = 1
net.ipv4.conf.br0.arp_announce = 2

net.ipv4.conf.enp7s0.arp_ignore = 1
net.ipv4.conf.enp7s0.arp_announce = 2

net.ipv4.conf.all.rp_filter = 0
net.ipv4.conf.br0.rp_filter = 0
net.ipv4.conf.enp7s0.rp_filter = 0
```

然后应用：

```bash
sudo sysctl --system
```

这里几个参数的作用大致如下：

```
arp_ignore = 1
```

表示只在目标 IP 配置在接收 ARP 请求的那个接口上时，才响应 ARP。

```
arp_announce = 2
```

表示发送 ARP 请求时，尽量使用最合适的本地地址，避免拿另一个接口的 IP 去做 ARP 宣告。

```
rp_filter = 0
```

表示关闭反向路径过滤。

在多网卡、多路径、策略路由场景下，`rp_filter` 很容易误判合法流量。如果不关闭，可能出现路由规则正确但包仍然被内核丢弃的情况。

***

### 九、主路由器上的端口转发也要改

Ubuntu 配好之后，主路由器上的端口转发目标也要对应调整。

原来如果端口转发到了：

```
192.168.1.10
```

现在应该改成：

```
192.168.1.99
```

例如：

```
WAN:443 → 192.168.1.99:443
WAN:80  → 192.168.1.99:80
```

这样外网请求才会从 `enp7s0` 进入 Ubuntu，并由 `192.168.1.99` 这条策略路由返回。

如果主路由器支持 DMZ，也可以把 DMZ 指向 `192.168.1.99`，但更推荐按需做端口转发，安全性更好。

### 十、最终流量路径

完成配置后，系统里实际上存在两条互不干扰的路径。

#### 1. 宿主机主动访问外网

```
Ubuntu br0 / 192.168.1.10
  → OpenWrt 旁路由 192.168.1.2
  → 主路由器 192.168.1.1
  → 外网
```

这条路径用于宿主机的普通出站访问。

#### 2. 外网访问宿主机服务

```
外网
  → 主路由器 192.168.1.1
  → Ubuntu enp7s0 / 192.168.1.99
  → Ubuntu 服务
```

回包路径是：

```
Ubuntu 服务
  → Ubuntu enp7s0 / 192.168.1.99
  → 主路由器 192.168.1.1
  → 外网
```

这样就避免了回包被错误地送到 OpenWrt 旁路由。

***

### 十一、为什么不直接把默认路由改回 192.168.1.1？

一个最简单的想法是：既然外网访问回包走 OpenWrt 会出问题，那直接把 Ubuntu 的默认路由改回主路由器 `192.168.1.1` 不就好了？

确实，这样可以解决外网访问问题。

但代价是：Ubuntu 宿主机自己的默认出站流量就不再经过 OpenWrt 旁路由了。

这和最初搭建旁路由的目标冲突。

我希望达到的是：

* 宿主机日常访问仍然走 OpenWrt
* 外网访问宿主机时，回包直接走主路由
* 两类流量互不影响

因此，策略路由才是更合理的方案。

***

### 十二、为什么不用 NAT 绕过去？

还有一种思路是在 OpenWrt 或 Ubuntu 上做额外 NAT，把回包伪装成某个地址，从而绕过路径不一致问题。

这种方式在某些场景下可以工作，但我不太推荐作为首选方案。

原因是：

1. NAT 会隐藏真实来源，排查问题更困难
2. 规则复杂之后，可维护性会下降
3. 一旦涉及多个服务、多个端口，容易出现隐性问题
4. 它没有从根本上解决入站路径和回包路径不一致的问题

相比之下，策略路由的逻辑更清晰：

```
谁进来的，谁出去。
哪个源地址，走哪张路由表。
```

这更符合网络设计本身的思路。

***

### 十三、排查建议

如果配置完成后仍然无法从外网访问，可以按下面顺序排查。

#### 1. 确认服务是否监听在 192.168.1.99

例如查看端口监听：

```bash
ss -lntp
```

如果服务只监听在 `127.0.0.1` 或 `192.168.1.10`，外网访问 `192.168.1.99` 自然不会成功。

建议服务监听：

```
0.0.0.0
```

或者显式监听：

```
192.168.1.99
```

#### 2. 确认主路由器端口转发目标

端口转发目标必须是：

```
192.168.1.99
```

而不是：

```
192.168.1.10
```

#### 3. 确认策略路由命中

执行：

```bash
ip route get 8.8.8.8 from 192.168.1.99
```

如果结果不是走 `192.168.1.1 dev enp7s0`，说明策略路由没有生效。

#### 4. 抓包确认流量方向

可以分别在两个接口上抓包：

```bash
sudo tcpdump -i enp7s0 -n
sudo tcpdump -i br0 -n
```

如果外网请求从 `enp7s0` 进来，但回包从 `br0` 出去，说明策略路由或源地址选择仍然有问题。

#### 5. 检查防火墙

如果 Ubuntu 上启用了 `ufw`、`iptables` 或 `nftables`，需要确认相关端口允许访问。

例如：

```bash
sudo ufw status
```

***

### 十四、总结

这次遇到的问题，本质上是 OpenWrt 旁路由场景里很常见的一个问题：

> 宿主机默认路由指向旁路由后，外网访问宿主机服务时，回包也会被送到旁路由，导致连接异常。

解决这个问题的关键不是简单地添加第二个默认网关，而是使用策略路由：

```
192.168.1.10 → 走 OpenWrt 旁路由 192.168.1.2
192.168.1.99 → 走主路由器 192.168.1.1
```

最终效果是：

* Ubuntu 宿主机仍然可以通过 OpenWrt 旁路由访问外网
* 外网可以正常访问 Ubuntu 宿主机上的服务
* 入站和出站路径保持一致
* 网络结构清晰，后续也更容易维护

对于虚拟化宿主机、OpenWrt 旁路由、内外网服务混合部署的场景来说，这种基于源地址的策略路由方案会比简单改默认路由或堆 NAT 更稳定、更可控。
